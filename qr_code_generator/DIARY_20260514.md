# Dev Diary — May 14, 2026

**Project:** QR Code Generator (build-moat-live-sessions)  
**Tool:** Claude Code (Sonnet 4.6)

---

Today I sat down with Claude Code to work through the QR Code Generator exercise from the live sessions repo. I wasn't sure how far I'd get, but we ended up finishing the whole thing — scaffold TODOs, bonus challenges, documentation, and all.

## How it went

Started by just asking Claude to read the README and tell me what tasks were in scope. Simple enough — but it immediately gave me a clean, structured breakdown instead of dumping the raw file at me. That set the tone for the rest of the session.

Then we read through `PROMPT.md` together. Before touching any code, Claude walked me through the five Design Questions one by one. This part was actually more valuable than the implementation itself. Things I hadn't thought to ask myself:

- Why 302 and not 301? (Browser caching kills analytics and makes URL updates useless.)
- Why encode the *short* URL in the QR code, not the long one? (So you can change the destination without reprinting anything.)
- What's the difference between 410 and 404? (One says "this existed and is gone," the other says "this never existed." Matters for SEO and client behavior.)

Good reminders that system design is mostly about *why*, not *what*.

## The implementation

The three scaffold TODOs — `generate_token()`, `validate_url()`, and `redirect()` — took maybe 20 minutes total. Claude wrote clean, minimal code without over-engineering. The one interesting bug we hit: tokens with an expiration date were being pre-warmed into the in-memory cache on create, so when you tried to redirect an expired link, the cache served it as a 302 instead of checking the DB and returning 410. 

The fix was simple once spotted: only cache tokens where `expires_at is None`. If there's an expiry, every redirect has to hit the DB to check whether it's still valid. It's a good example of how caching introduces subtle correctness bugs — the hot path optimization broke the expiry semantics entirely.

## Bonus challenges

Knocked out all three:

1. **Frontend** — a single `HTMLResponse` route at `/`, no extra dependencies. Input a URL, pick an optional expiry time, get back a QR code image and short URL.
2. **Rate limiting** — `slowapi`, 10 requests per minute per IP on the create endpoint. Hit the 11th and you get 429.
3. **Expiration** — already half-done in the scaffold, just needed the cache bug fixed and verification tests.

## What I appreciated about working with Claude Code

It didn't ask me what I wanted to do next after every step — it read the context and moved. When I said "start implementing the TODOs," it looked at all three files first, then wrote all three implementations before running a single test. The verification curl tests ran in one shot and passed cleanly.

The data topology diagram was a nice surprise. I asked for it almost as an afterthought, and it came back with a full Mermaid flowchart showing exactly where data lives (SQLite vs in-memory dict), how the cache and DB interact, and where the scan counter actually sits (no dedicated counter column — just `COUNT(*)` over `scan_events`). Saved me from having to trace the code manually.

## Things I'd do differently next time

- Set up the venv before starting, not mid-session.
- Read `database.py` earlier — understanding the persistence model before writing routes would have caught the cache bug before it happened.
- The in-memory `redirect_cache` dict is fine for a prototype but would need to be Redis or equivalent in production. Worth noting in the design doc.

## Closing thought

The exercise is well-designed. The scaffold forces you to make real decisions (not just fill in blanks), the verification tests are concrete and runnable, and the bonus challenges extend naturally from the core. Using Claude Code as a pairing partner made it faster, but more importantly it made the *thinking* more explicit — especially the design question answers, which I might have skimmed past if I were coding alone.

Good session.
